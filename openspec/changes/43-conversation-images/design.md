## Context

Claude Code writes images into the transcript as content blocks `{ type: "image", source: { type: "base64", media_type, data } }`: directly in a user message next to the prompt text, or inside `tool_result.content` next to text blocks (screenshots, `Read` of an image). A single base64 string is often tens of KB and can reach several MB. `parser.ts` is the only module that knows this format and maps both to `[imagem]`. `TranscriptFile` keeps the byte offset of every line, so one line can be read again cheaply (`readLines(cursor, cursor + 1)`). Entries are streamed (`transcript.entry`) and paged (`transcript.page`); the app keeps them in the transcript store and builds the timeline from them.

## Goals / Non-Goals

**Goals:** show user and tool images on iOS and Android; keep the stream and the pages small; never freeze the list; no hardcoded placeholder text.

**Non-Goals:** images in assistant messages (Claude Code does not write them); remote (`url`/`file`) image sources; thumbnails generated by the daemon (it would need an image library); saving or sharing images from the viewer.

## Decisions

- **References in entries, data on demand.** Entries carry `ImageRef { id, mediaType, bytes }` only; inlining even small images would bloat every page and reconnect. `bytes` is computed from the base64 length, so the app can skip the fetch for images over the limit. `images` defaults to `[]` in the schema: older daemons validate, and older apps strip the unknown key.
- **Image id = `<cursor>.<n>`**, where `n` is the image's position among the line's image blocks in document order (top-level blocks and those inside `tool_result.content`). It needs no state in the daemon, survives restarts, and the parser that numbered the images can find the `n`-th one again (`findImage(raw, n)`). The app keys its cache by stream and image id.
- **Where images attach.** A user line's top-level images attach to the last prompt text entry of that line; without prompt text, to the line's last `tool_result` (an image next to a result belongs to the tool, not to the user); otherwise to a new `user` entry with empty text. Images inside a `tool_result` attach to that result; its text stays the text blocks only. Numbering and `findImage` walk the same blocks: top level, and tool results one level deep.
- **`transcript.image` request** (`sessionId`, optional `agentId`, `imageId`) resolves the transcript like `session.history`, reads that one line and answers `{ imageId, mediaType, data }`. It returns `not_found` when the id is malformed or the block is gone, `too_large` above `MAX_TRANSCRIPT_IMAGE_BYTES` (5 MB, the Claude API's own image limit, which also keeps replies from holding the socket for long). Read-only: it works for sessions without a tmux pane.
- **No stolen lines.** `TranscriptFile.sync()` returns appended lines only once, and history pages used to call it on the same file object a live stream pumps, so lines read there never reached the subscribers. History and images now catch up through the stream's pump when one exists (`catchUp`); an image ref always comes from an indexed line, so the image read needs no sync at all.
- **App loading.** `useTranscriptImage(ref)` runs when the thumbnail mounts (FlashList only mounts what is near the viewport, which makes it lazy). A pure module (`image-cache.ts`) holds an LRU of data URIs capped by size (32 MB of base64) and a queue that runs at most 2 fetches at a time, newest first (the thumbnails on screen), de-duplicates requests for the same image and drops a waiting fetch once every thumbnail that wanted it unmounted (a fling through a long history does not fetch everything it passed). Refs over the limit render the "too large" state without fetching. While disconnected the hook waits (it re-runs when the connection is back); other failures show a message and retry on tap. The request timeout grows with the image size (15 s plus about 100 KB/s).
- **Fixed-size thumbnails** (120 pt tall, up to 160 pt wide, `contain`), so loading never changes the item height and the list does not jump. Several images wrap in a row. The strip's "viewer open" state uses FlashList's `useRecyclingState`, so a recycled cell never inherits an open viewer.
- **Viewer** is a `Modal` with its own `GestureHandlerRootView` (needed on Android inside modals). Pinch zoom (1x to 5x), pan while zoomed, double tap toggles 1x/2.5x, all on the UI thread with Reanimated. Back on Android closes it through `onRequestClose`. No new native dependency: React Native `Image` renders `data:` URIs on both platforms.
- **Context for the conversation.** Timeline items are rendered by a module-level `renderItem`; a small React context (`TranscriptImagesContext`) gives image components the `sessionId` and `agentId` of the conversation.
- **Tool JSON tab** lists the image refs (id, type, size), not the data. Prompt history lists image-only prompts as "N images".

## Risks / Trade-offs

- [Big images held in JS memory as base64, copied to native by `Image`] → cache capped by size, eviction by least recent use, at most a few thumbnails mounted at once; writing files with `expo-file-system` would be leaner but needs a new native dependency and build.
- [GIF animation on Android] → React Native shows GIFs on Android only as a still frame without extra Fresco modules; acceptable for a preview.
- [Older app with a newer daemon shows image-only prompts as empty] → the app updates over the air; the daemon change is announced in the release.

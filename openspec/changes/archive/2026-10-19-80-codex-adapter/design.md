## Context

The daemon is driven by hook events (`HookReceiver` → bus `hook` → sessions, push, live status, subagents; `PermissionRequest` held open by the broker), by transcripts (`TranscriptService`, one parser) and by the tmux pane (input, keys, mode detection). `AgentAdapter` (change 66) carries only the command, config dir variable, resume/worktree args and transcripts dir; launcher, hooks installer, transcript parser, recent scan and commands are Claude Code specific.

Facts about Codex CLI 0.163 used here (read from `openai/codex` at `fbb2f9d`):
- Rollouts: `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<local time>-<uuid>.jsonl`, created at the first prompt. Lines are `{timestamp, ordinal?, type, payload}`. The first line is `session_meta` (`id`, `cwd`, `history_mode`). Paginated rollouts (`ordinal` on every line, the TUI default) keep the conversation as `event_msg` `item_completed` items (`UserMessage`, `AgentMessage`, `Reasoning`, …); legacy rollouts as `event_msg` `user_message` / `agent_message` / `agent_reasoning`. Both keep tool calls as `response_item` `function_call` (`exec_command` `{cmd, workdir}`, older `shell`), `custom_tool_call` (`apply_patch`, the patch as `input`), `local_shell_call`, `web_search_call`, and their outputs by `call_id`. `task_complete` (`duration_ms`), `turn_aborted`, `compacted`, `turn_context` and `thread_settings_applied` (`approval_policy`) are persisted. Approval prompts never are.
- Hooks: `$CODEX_HOME/hooks.json` `{hooks: {Event: [{matcher?, hooks: [{type: "command", command, timeout}]}]}}`, run as `$SHELL -lc` with the event JSON on stdin and Codex's environment (`TMUX_PANE` and the launcher's variables included). `PermissionRequest` output `{hookSpecificOutput: {hookEventName, decision: {behavior, message?}}}` decides; empty output, failure or timeout falls back to the TUI prompt; `updatedPermissions` / `updatedInput` count as failure. `SessionEnd` hooks get at most 3 s. New or changed hooks run only after the user trusts them once ("Hooks need review").
- TUI: Enter submits; bracketed paste works; typed bursts followed by Enter within 120 ms become a newline. `codex resume <id>` resumes; `-m` picks the model.

## Goals / Non-Goals

**Goals:**
- Codex sessions in the list (live and recent), their conversation, prompts and keys, start and resume from the phone, permission requests answered from the phone, push and live status, with Claude Code behavior unchanged.
- Each format known by one module; the adapter interface only grows with what actually differs.

**Non-Goals:**
- Changing Codex permissions from the app (the `/permissions` menu is driven from the terminal view). A later change can use the Codex app-server (`thread/settings/update`) once its handshake is verified.
- Codex subagents, skills in the command list (`$skill` syntax), provider profiles for Codex, the app-server socket.

## Decisions

- **Adapter interface.** `AgentAdapter` gains: `transcript: TranscriptFormat`; `findTranscripts(configDir, cutoffMs)` → `{sessionId, path, mtime}[]`; `readSummary(path, configDir)` → `{title, cwd, permissionMode, approvalPolicy}`; `commands(configDir, cwd)` + `commandsSignature`; `input: {minEnterDelayMs, newline: {literal?, keys}, beforeSubmit}`; `hooks: {style: 'claude-settings' | 'codex-hooks', file(configDir)}`; `statusLine`, `providers`, `modes` and `permissionRules` flags. `adapterOf(agent)` picks the adapter of a session record (Claude Code when absent). Callers pick the adapter from the session's profile (`agentFor`). Claude Code keeps its values; its functions move behind the interface unchanged.
- **One parser per format.** `TranscriptFormat` (`parseLine`, `parseMeta`, `findImage`) is injected into `TranscriptFile` and `StreamTarget`; the Claude Code parser is `claudeTranscript`, the Codex one `codexTranscript` in `codex-format.ts`.
- **Codex lines without duplicates.** A line with `ordinal` is paginated: messages come from `item_completed` (`UserMessage` text and data-URL images, `AgentMessage`, `Reasoning` summary, `Plan`, `ContextCompaction`); without `ordinal`, from `user_message` / `agent_message` / `agent_reasoning`. `response_item` messages and reasoning are ignored in both (they repeat the above plus injected context). Tool calls always come from `response_item`s, so a running command shows before it ends: `exec_command` / `shell` / `shell_command` / `local_shell_call` → `tool_use` `exec` `{command, workdir}`; `apply_patch` → `tool_use` `apply_patch` `{files, patch}` (files from the `*** Add/Update/Delete File:` headers); other functions keep their name and parsed arguments; `web_search_call` → `web_search` `{query}`. Outputs → `tool_result`; for exec, the `Output:` section is the content and a non-zero `Process exited with code N` marks an error. `task_complete` → `turn_duration`, `turn_aborted` → system `turn_aborted`, `compacted` → `compact_boundary`. Lines have no uuid, so keys are `line-<cursor>:<index>`. Image ids are `<cursor>.<n>` over the data-URL images of the user message, as for Claude Code.
- **Mode.** `Session.approvalPolicy` (`on-request`, `never`, `untrusted`, `granular`; null for Claude Code) comes from the newest `turn_context` / `thread_settings_applied` while streaming (`parseMeta`) and from the rollout tail in `readMeta`. `session.setMode` on a Codex session answers `bad_request`. The app's chip shows the policy, read-only, with an accessibility label.
- **Hooks.** For Codex profiles the installer merges into `<CODEX_HOME>/hooks.json` one group per event (`SessionStart`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SessionEnd`) with a `curl` command hook posting stdin to `/hooks/<Event>` with the secret, `$TMUX_PANE` and `$CLAUDE_REMOTE_PROFILE` headers, the same detection (`isOurHook`) and removal rules as Claude Code's settings. `PermissionRequest`'s curl prints the daemon's answer (timeout `hookPermissionTimeoutSec`); the others discard output, `SessionEnd` uses `-m 2` and timeout 3. The trust prompt is explained in setup's output, doctor and the docs.
- **Permissions.** The broker gives Codex requests no suggested rule and never `updatedPermissions` / `setMode` (Codex would treat them as a failure), so the app offers Allow / Deny only. Expired or cancelled requests still return `{}`, handing the prompt back to the TUI.
- **Input.** `InputService` waits `max(pasteEnterDelayMs, adapter.input.minEnterDelayMs)` before Enter (Codex: 250 ms) and, for the `type` strategy, uses the adapter's newline keys (Codex `C-j`, Claude Code `\` + Enter) and pre-submit keys (Claude Code `Escape` to close menus; none for Codex, where a stray Esc arms "edit previous message").
- **Launcher.** The config-dir lines come from the adapter (`CODEX_HOME`; the default `~/.codex` runs with the variable unset), the binary defaults to the adapter's command, and the provider block is Claude Code only. `codex` joins the reserved aliases.
- **Setup.** `detectConfigDirs` also returns `~/.codex` when it holds `config.toml`, `auth.json` or `sessions`; `suggestProfile` gives it `agent: 'codex'`, id `cdx`, name `Codex` and the Codex color. Doctor checks `codex` on the PATH when a profile uses it, and that the Codex hooks are installed.

## Risks / Trade-offs

- [The rollout format is internal to Codex and changes between versions] → the parser is defensive (unknown lines are skipped or become `unknown` entries) and has fixture tests built from the 0.163 structs.
- [Codex hooks need a one-time trust in the TUI; until then sessions are read-only and approvals stay in the terminal] → told by setup, doctor and the docs; nothing breaks meanwhile.
- [Overriding nothing in `config.toml`] → the user's Codex config stays untouched; only `hooks.json` is written, with a backup.
- [Approval policy alone does not tell Read Only from Ask for approval] → acceptable for the chip; the sandbox can be added later.

## Context

The composer (`apps/mobile/src/features/conversation/components/PromptComposer.tsx`, wrapped by `apps/mobile/src/features/autocomplete/SmartComposer.tsx`) is a plain controlled `TextInput` plus a send button; `usePrompt` (`features/conversation/use-prompt.ts`) owns the text state and the `session.input` request. Issue #40 asks to add voice recording that transcribes into this same field, and explicitly asks to compare three transcription approaches in the OpenSpec change:

1. **On-device speech recognition** (iOS Speech framework / Android `SpeechRecognizer`): private, free, works offline in many languages; quality depends on the OS.
2. **On the computer**: stream the audio to the daemon and transcribe there (e.g. `whisper.cpp`), so audio never leaves the user's own machines.
3. **A cloud API**: explicitly the least preferred option in the issue, since the app avoids sending session content to third parties.

## Goals / Non-Goals

**Goals:**
- Recording and transcription that works the same way on iOS and Android (the app is cross-platform since change 25).
- Nothing about a voice message — audio or transcript — leaves the phone, consistent with the project's existing privacy stance (WS only over Tailscale, push never carries session content, `bypassPermissions` never offered).
- The transcript behaves exactly like typed text: it only fills the field, the existing send button and `usePrompt` are unchanged.
- Permission and UI text localized in pt-BR/en-US/es-ES, like every other user-facing string.

**Non-Goals:**
- Daemon-side or cloud transcription (see Decisions — dropped for this change).
- A slide-to-cancel gesture or a press-and-hold-to-record interaction: tap-to-start/tap-to-stop with explicit Cancel/Done buttons is simpler to implement correctly and more accessible (VoiceOver, external keyboard, Android back button), at the cost of one extra tap versus a WhatsApp-style hold. Revisit only if real usage shows the extra tap is a problem.
- Redesigning the composer's send button into a WhatsApp-style mic-when-empty / send-when-typing control — that is issue #41's separate scope. This change only adds a dedicated microphone button alongside the existing one.
- Automatic spoken-language detection (see Decisions — not reliable enough across both platforms to replace a manual choice) and a transcription engine/quality setting.

## Decisions

- **On-device recognition, not daemon-side or cloud.** Dropping option 3 (cloud) is direct: it conflicts with the project's privacy stance, and the issue itself calls it least preferred. Option 2 (daemon-side `whisper.cpp`) was considered more seriously, since the daemon already does comparable local work (tmux, hooks) — but it would need: new `packages/protocol` messages to stream audio from app to daemon, a `whisper.cpp` binary or binding packaged and kept working across macOS, Linux and WSL (three different native build/runtime setups, not just three `if` branches), a model download/management story mirroring `platform-support`'s installer work, and a Tailscale round-trip for every recording even though the daemon and app are already paired — all to reach roughly the same transcription quality tier as on-device, with a much larger surface. Option 1 (on-device) needs none of that: it is a pure mobile-app feature with no daemon or protocol change, and it keeps audio on the phone by construction, not merely by configuration (nothing to leak if the network degrades). The issue's own "quality depends on the OS" trade-off is accepted.
- **Library: `expo-speech-recognition` (jamsch), not `@react-native-voice/voice`.** It is built specifically for Expo (config plugin, works with Continuous Native Generation, no eject), actively published against the project's current SDK line (57.1.1, matching Expo SDK 57), and wraps exactly the two platform APIs the issue names: iOS `SFSpeechRecognizer` and Android `SpeechRecognizer` (plus a web `SpeechRecognition` shim the app does not use). `@react-native-voice/voice` is older, not Expo-specific, and updated less recently. `requiresOnDeviceRecognition: true` is passed to `start()` so recognition stays local whenever the OS supports it; Android 13+ needs its offline language model downloaded first (`androidTriggerOfflineModelDownload()`) — see Risks.
- **The library's own `volumechange` event drives the level meter; no extra audio library.** `expo-speech-recognition` emits `{ value: number }` (roughly -2 to 10) at a configurable interval during recording, which is exactly the "visible level" the issue asks for. No need for `expo-av`/`expo-audio` or a second recording path just for metering.
- **Recognition locale is a separate, persisted setting that defaults to the app's i18n language, not a fixed mirror of it.** `start({ lang })` takes a BCP-47 tag; the app's own `Locale` type is already `pt-BR`/`en-US`/`es-ES`, the exact tags the module expects. First shipped as "always `currentLocale()`" (matching the device's UI language one-to-one), real usage surfaced the gap: someone running the app in English while speaking Portuguese got transcripts in the wrong language with no way to fix it. Settings now offers "same as the app" (default, calls `currentLocale()` at record time) or a fixed `pt-BR`/`en-US`/`es-ES`, persisted in `SecureStore` the same way `channel` is in `core/updates/updates.ts` (`restoreVoiceLanguage()`/`setVoiceLanguage()` mirror `restoreChannel()`/`switchChannel()`).
- **No automatic spoken-language detection.** `expo-speech-recognition` exposes Android's `EXTRA_ENABLE_LANGUAGE_DETECTION`/`EXTRA_ENABLE_LANGUAGE_SWITCH` (`AndroidIntentOptions`), but its own docs say the corresponding language model "must be downloaded to support the switch. Otherwise, the recognizer will report an error" and "depending on the recognizer implementation, this value may have no effect" — and there is no equivalent at all on iOS (`SFSpeechRecognizer` always recognizes against one fixed locale per request). A feature that silently works sometimes on some Android devices and never on iOS would be worse than no feature; a manual, predictable choice with "same as the app" as the one-tap default covers the reported need (app in one language, dictating in another) without that gap.
- **Permission text must be set explicitly on both plugins that touch `NSMicrophoneUsageDescription`, not left to rely on plugin order.** `expo-camera`'s plugin option `microphonePermission: false` (today, since the camera is QR-only) actively **suppresses** that Info.plist key — `false` is a delete directive, not a no-op, confirmed by reading `expo-camera`'s own plugin source (`IOSConfig.Permissions.createPermissionsPlugin` treats `false` as "remove the key"). `expo-speech-recognition`'s plugin sets the same key to its own default/custom string. Whichever of the two plugins runs last would otherwise decide the outcome. The fix: pass the real description (`SYSTEM_PROMPTS.en.NSMicrophoneUsageDescription`, a new entry) to **both** `expo-camera`'s `microphonePermission` and `expo-speech-recognition`'s `microphonePermission` options, so the result is correct regardless of order. `NSSpeechRecognitionUsageDescription` has no such conflict (only `expo-speech-recognition` touches it). The per-language override text (pt-BR/en-US/es-ES) is added to `SYSTEM_PROMPTS`/`locales`, the same mechanism already used for the camera and local-network prompts.
- **`android.permission.RECORD_AUDIO` moves off the blocked list.** It is listed today in `ANDROID_BLOCKED_PERMISSIONS` because nothing needed it; `expo-speech-recognition`'s plugin adds it back via `AndroidConfig.Permissions.withPermissions`, which would conflict with the app's own block list the same way the iOS key does. Simplest fix: remove it from `ANDROID_BLOCKED_PERMISSIONS`.
- **New `src/features/voice` module, side effects isolated behind a hook.** Pure helpers — mapping a `volumechange` value to a 0-1 meter level, formatting the elapsed timer, mapping an app `Locale` to the recognition `lang` tag — live in plain `.ts` files with Vitest tests, per the project's convention (pure logic separate from `react-native`-touching code). A `useVoiceRecording()` hook wraps `expo-speech-recognition`'s module and events (start/stop/cancel, level, timer, final transcript, permission state) and is the only side-effecting piece; `SmartComposer` calls it and inserts the transcript into `prompt.text` the same way `SuggestionList` insertion already does.

## Risks / Trade-offs

- [Android 13+ requires an offline language model download before on-device-only recognition works, and the download can fail or be skipped] → `start()` without `requiresOnDeviceRecognition` still works (falls back to Android's online recognizer); detect via the `error` event (`code: "language-not-supported"` or similar) and offer to retry rather than silently sending audio over the network — the fallback must still ask the user, never transcribe online without them knowing.
- [`expo-speech-recognition` is a community package, not an official Expo module] → it is the closest fit to the issue's own requirements and is actively maintained against the project's current SDK; if it stops being maintained, the native hookup is isolated to the `useVoiceRecording` hook and a config plugin entry, not spread across the composer.
- [iOS Simulator / Android Emulator microphone support is inconsistent] → manual verification note for tasks.md; this project's development build already runs on real devices for anything hardware-dependent (camera, push).
- [Recognition quality varies by OS, device and language, especially for code-heavy prompts (identifiers, paths)] → accepted per the issue; the transcript is always editable before sending, same as any typed text.

## Context

`colors` is a frozen object imported by 57 files and used inside `StyleSheet.create` at module load, in inline styles and in a few pure helpers (`LEVEL_COLORS` in `session-status/logic.ts`, `grouping.ts`). Dark is also hard-coded in `expo-status-bar`, `ActionMenu` (`userInterfaceStyle`), `react-native-marked` (`colorScheme`), the xterm.js HTML baked by `scripts/build-xterm-html.mts`, the sheets' backdrop (`#000000AA` in six files) and the Live Activity layout, which runs in the widget runtime and cannot import app state (colors are literals there). The prototypes (`docs/design/identity/index.html`, "Tokens") list the five palettes; only Dark is implemented here.

## Goals / Non-Goals

**Goals:** every color read from the current theme at render time; a theme switch (later) re-renders the whole app without a restart; dark looks like today except the accent and warning swap; agent colors available as fixed tokens; no hex literal outside the theme module.

**Non-Goals:** the Light, Dracula and Catppuccin palettes and the Appearance selector (#111, #157); the new icons and splash (#84); the agent badge component (#153); re-registering a running live status when the theme changes.

## Decisions

- **Theme shape.** `Theme = { name: ThemeName; scheme: 'dark' | 'light'; colors: ThemeColors; ansi: AnsiColors }`, each theme a module constant so object identity is stable (`THEMES[name]`). `ThemeColors` is a closed record type: adding a token to the type forces every palette to define it (compile-time parity), and `palettes.test.ts` also checks at runtime that every value is a `#RRGGBB` or `#RRGGBBAA` color and that `ansi` has the 16 keys. `scheme` is what the system-facing pieces need (status bar, action sheet, markdown, keyboard appearance).
- **Token names.** The existing names stay, `*Muted` fills become `*Soft` (matching the prototype and the issue), and three tokens are added: `accentText` (accent used as text or icon; equal to `accent` in dark, darker in light themes), `accentInk` (text on an accent fill; the primary button used `background`, which breaks on light themes) and `backdrop` (the sheets' scrim, previously a literal in six files). Rule of use: fills, borders and dots use `accent`; text and icons use `accentText`.
- **Agent colors** live in `core/theme/agents.ts` (`AGENT_COLORS: Record<AgentId, string>`, `AgentId = 'claude' | 'codex' | 'kimi' | 'qwen'`), outside the themes because they identify the agent in every theme. Nothing uses them yet besides the token test; #153 adds `AgentBadge`.
- **Preference store.** `useThemeStore` (Zustand) holds `preference: 'system' | ThemeName` and `system: 'light' | 'dark'`; `resolveThemeName(preference, system)` is a pure function with tests (with only `dark` available, every input resolves to `dark`; #111 extends the table). The preference is persisted in SecureStore under `remote-harness.theme`, like the other per-device switches, and restored at start with the others. `ThemeProvider` (root layout) mirrors `useColorScheme()` into the store, sets the root view background (`expo-system-ui`) and renders the `StatusBar` with the style of the current scheme.
- **`useTheme()` and `makeStyles`.** `useTheme()` selects `THEMES[resolveThemeName(...)]` from the store. `makeStyles(factory)` returns a hook that caches `StyleSheet.create(factory(theme))` per theme object in a `WeakMap`, so styles are built once per theme and components only re-render on a theme switch. Components that need a color in JSX (icons, inline styles) read `const { colors } = useTheme()`. Pure helpers keep returning token names (`ColorName`), never values.
- **Markdown.** The `theme` object and styles of `react-native-marked` are built per theme (`useMemo` on the theme) and `colorScheme` follows `theme.scheme`.
- **Terminal.** The HTML no longer bakes the palette: it reads `window.__theme` (injected with `injectedJavaScriptBeforeContentLoaded`) at start and exposes `window.setTheme(theme)` for live switches, applying the xterm theme, the page and viewport background. `TerminalView` builds the xterm theme from `theme.colors` and `theme.ansi` (`foreground = text`, `cursor = accent`, `selectionBackground = accentSoft`). The dark ANSI values are the ones baked today, so the terminal looks the same.
- **Live Activity.** `LivePaletteSchema { background, text, textMuted, accent, success, warning }` is optional on `LiveStatusProps` and on `live.register`. The app fills it from the current theme when it starts an activity (local props) and when it registers; the daemon stores it with the registration and spreads it into every `liveProps` it sends, so remote updates never reset the colors. The widget reads `props.palette` with the dark literals as fallbacks (payloads from older daemons), which is the one place allowed to keep hex literals outside the theme module.
- **Guard test.** `no-hardcoded-colors.test.ts` walks `apps/mobile/src` and fails on `#RGB`, `#RRGGBB` or `#RRGGBBAA` literals outside `core/theme/`, excluding `*.generated.ts`, `*.test.ts` and `features/live-status/SessionActivity.tsx`. The check is a Vitest test instead of a Biome rule because Biome has no "no literal color" rule and a regex over the tree is enough.
- **Status gauges.** `LEVEL_COLORS.warning` goes from `accent` to `warning`: with amber as the brand color, a 70% gauge in the accent would look like a highlight, not a warning.
- **Unknown profile color.** `groupSessions` stops inventing `#8A8784` for sessions of unknown profiles (`color: ''`); `ProfileHeader` and the Settings list fall back to `textMuted` when the color is empty.
- **`app.config.ts`.** `userInterfaceStyle: 'automatic'` so system surfaces (alerts, pickers) can follow the user; the Android notification accent becomes amber; splash and adaptive icon backgrounds stay dark until #84 replaces the artwork.

## Risks / Trade-offs

- Touching 57 files is mostly mechanical but easy to get subtly wrong (a missed `colors.` becomes a type error, which is the safety net: the static export is removed).
- The widget layout cannot be unit-tested; the palette access is written as plain property reads with a ternary fallback, the same constructs the layout already uses.
- Until #111 lands, `preference: 'system'` always resolves to dark, so `userInterfaceStyle: 'automatic'` only affects system surfaces.

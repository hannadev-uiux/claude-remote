## Context

`TmuxClient.focusPane` (`apps/daemon/src/infra/tmux.ts:95`) only runs `select-window`/`select-pane`, which changes tmux's internal "current" window/pane but never touches which terminal client is looking at which session, and never raises any window on screen. It is called from `features/pane/index.ts`'s `pane.focus` handler and from the tray's `focusSession` in `features/updates/index.ts:310`. `Desktop.runInTerminal` (`apps/daemon/src/infra/desktop.ts`) already opens a new terminal window running a given command, but only for `doctor` and only via a single hardcoded app per platform (`Terminal` on macOS via AppleScript, `x-terminal-emulator` on Linux, a no-op under WSL). Neither path checks `tmux list-clients` to see whether a terminal is already attached.

## Goals / Non-Goals

**Goals:**
- Make "Open in terminal (tmux)" (the renamed tray action) actually show the session on screen in both cases the issue describes: a terminal already attached (possibly to another session) and no terminal attached at all.
- Keep the command-building logic (which app, attach vs. switch, the literal command per app) pure and unit-tested with Vitest, per the issue's own notes; only the actual process spawn is a side effect.
- macOS gets real multi-app support (iTerm2, Ghostty, WezTerm, kitty, Alacritty, Terminal.app); Linux and WSL get a best-effort equivalent using what is already there (`$TERMINAL`/`x-terminal-emulator`, `wt.exe`).

**Non-Goals:**
- A **Preferences** override of the detected terminal app (issue #248 mentions it, but Preferences (#230) does not exist in this codebase yet — out of scope here, revisit when #230 lands).
- Raising a specific existing window of a multi-window terminal app to the front (macOS can only activate the application, not a particular window, without extra accessibility permissions not asked for here).
- Any change to the `pane.focus` protocol message shape — it keeps taking only `sessionId`.
- A UI affordance in the app for this action — issue #248's "app's session menu" does not exist yet; only the tray consumes this today.

## Decisions

- **tmux learns two primitives, nothing fancier.** `TmuxClient.listClients(target)` wraps `tmux list-clients -t <target> -F "#{client_tty}"` (empty array when the tmux server itself is absent, same convention as `listPanes`); `switchClient(clientTty, target)` wraps `tmux switch-client -c <clientTty> -t <target>`. Both take a `paneId` as `target` — tmux resolves a pane id to its containing session for every target type, the same way `focusPane` already does today, so no extra lookup of the session's name is needed.
- **A pure planning module decides what to run, not just whether to run it.** `apps/daemon/src/features/pane/terminal-focus.ts` exports `planShowInTerminal(input): ExecStep[]`, where `ExecStep = { file: string; args: string[] }`. Given the platform, WSL info, whether a client is already attached, the list of currently running process names (macOS only) and the pane/session ids, it returns the exact command(s) to run — including the full AppleScript or CLI arguments per app. `infra/desktop.ts` only executes the returned steps (`exec(step.file, step.args)`); it contains no app-specific strings itself beyond what already exists for `notify`/`open`/`runInTerminal`. This matches the issue's own note ("command building … as pure functions with Vitest tests; process calls in infra/") and the project's existing split between pure logic and injected effects.
- **macOS app detection by running process name, not by which client owns which tty.** Mapping a tmux client's tty to the specific OS window/app that holds it needs extra OS-level lookups (e.g. walking process trees or using Accessibility APIs) that are disproportionate here; in practice a machine runs one terminal app at a time. `pickTerminalApp` picks the first app, in a fixed priority order (iTerm2, Ghostty, WezTerm, kitty, Alacritty, Terminal.app), whose process name appears in the list returned by `tell application "System Events" to get name of every process whose background only is false`. When none of the five GUI-forward apps are running, it falls back to Terminal.app, which ships with every Mac. The same pick is used both to activate (client already attached) and to open a new window (no client attached).
- **Per-app command shapes**, verified against each app's current CLI/AppleScript docs:
  - **Terminal.app**: existing two-`osascript -e` pattern (`do script "<cmd>"`, then `activate`), reused from `runInTerminal`.
  - **iTerm2**: `osascript -e 'tell application "iTerm2" to create window with default profile command "<cmd>"'`; activate via `tell application "iTerm2" to activate`.
  - **Ghostty**: `open -na Ghostty --args -e sh -c '<cmd>'` (Ghostty's `-e` takes the remaining arguments as the command to run instead of the default shell); activate via `open -a Ghostty`.
  - **WezTerm**: `wezterm start -- sh -c '<cmd>'` (the bundled/PATH `wezterm` CLI, not `open`, since WezTerm's own CLI launches its GUI); activate via `open -a WezTerm`.
  - **kitty**: `open -na kitty --args sh -c '<cmd>'` (kitty runs trailing arguments as the window's command); activate via `open -a kitty`.
  - **Alacritty**: `open -na Alacritty --args -e sh -c '<cmd>'` (`-e`/`--command` must be the last argument); activate via `open -a Alacritty`.
  - The attach command itself is always `tmux attach -t '<paneId>' \; select-window -t '<paneId>' \; select-pane -t '<paneId>'`, shell-quoted; a pane id is enough for every clause, same reasoning as above.
- **Linux**: reuse `$TERMINAL` when set, else `x-terminal-emulator`, running the same attach command (`-e sh -c '<cmd>; exec "$SHELL"'`, matching the existing `runInTerminal` behavior) when no client is attached. When a client is already attached, only `switch-client` runs — there is no portable way to raise a specific window across Linux desktop environments without extra tools (`wmctrl`/`xdotool`) this project does not depend on, so this case intentionally does less on Linux than on macOS.
- **WSL**: `wt.exe wsl.exe sh -c '<cmd>'` for the "no client attached" case, relying on WSL interop to resolve `wt.exe` from the Windows `PATH` (same assumption the rest of the daemon makes about interop). The "already attached" case is a no-op on WSL for the same reason as Linux above (no window-raise primitive), beyond the `switch-client` tmux already does.
- **Errors propagate instead of being swallowed.** Unlike `desktop.ts`'s existing `ignore()` helper (used by `notify`/`open`/`doctor`'s `runInTerminal`, which drop every error), the new code lets a failed `exec` (and a failed `switchClient`/`focusPane`) throw. The tray's `onTrayClick` already wraps every action in a `try/catch` that logs `'tray action failed'`; the `pane.focus` WS handler already propagates handler errors as a normal WS error reply. Routing through these two existing paths satisfies the issue's "errors are shown … instead of failing silently" without inventing a new error channel for a daemon feature that, today, has none.

## Risks / Trade-offs

- [Guessed CLI flags for Ghostty/WezTerm/kitty/Alacritty could be wrong on some future version] → Mitigation: each is verified against that project's current documented CLI (checked during this change); the pure planner is unit-tested against the exact argument arrays, so a future flag change is a one-line test+code fix, not a silent regression.
- [Picking "the running app" by process name can activate the wrong app if the user runs two terminal apps at once, one of them not attached to tmux at all] → Mitigation: accepted — this is already a known limit called out in the issue itself ("in practice a machine runs one terminal app at a time" holds for the vast majority of setups); no existing code in this project does better.
- [`wezterm`/`$TERMINAL` may not be on the daemon's `PATH` under a service manager] → Mitigation: same class of problem `runInTerminal`'s `x-terminal-emulator` already has today; out of scope to fix PATH resolution generally in this change.

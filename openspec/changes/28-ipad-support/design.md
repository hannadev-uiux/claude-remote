## Context

Today `(main)/_layout.tsx` is a single Expo Router `Stack`: all navigation is screen-by-screen, in a stack, regardless of window size. `app.config.ts` has `supportsTablet: false` and `orientation: 'portrait'` (see proposal.md - Why). There is no breakpoint/width-class infrastructure in the project; the theme tokens (`src/core/theme/tokens.ts`) are fixed and built for the terminal aesthetic, not for scaling with the system. iPad support is inherently iOS/iPadOS-specific (Android has no equivalent device class), so this change's decisions are scoped to iPhone/iPad regardless of the app's own cross-platform support.

## Goals / Non-Goals

**Goals:**
- A single width-class mechanism (compact/regular) that other features consult, instead of each screen reinventing its own breakpoint logic.
- A master-detail layout that reuses the existing screens and routes (no duplicating `session/[id]`, `new`, `settings`, etc. into an "iPad version").
- Landscape support on iPad only, without changing iPhone behavior.

**Non-Goals:**
- Dynamic Type / system font scaling: `fontSize` values stay fixed. The terminal aesthetic depends on predictable column alignment with JetBrains Mono; scaling that by the system's text size is its own project, not part of this layout compatibility work.
- Resizing the tmux pane (`pane.frame`'s `cols`/`rows`, see `openspec/specs/raw-terminal/spec.md`) to match the screen size. The raw terminal keeps receiving frames at the pane's current size; on iPad it only makes better use of the available detail pane (scale/scroll adjustment), without asking the daemon to resize the real pane — that would change the output other tools (a direct `tmux attach`, other clients) see from the same pane.
- User-customizable keyboard shortcuts: the shortcuts are fixed (Cmd+N, Cmd+,, Esc, Cmd+Enter), with no preferences screen.
- Presentation of `new` (new session) and the permission alerts: `new` stays a modal (`presentation: 'modal'`) and `app-permissions`'s alerts stay as they are — both already behave well on iPad since the system sizes them natively; only the main navigation (list ↔ conversation ↔ terminal ↔ subagent ↔ settings) gets the master-detail treatment.

## Decisions

- **Width class by a point breakpoint, not by `UITraitCollection`.** A single hook (`useWidthClass()`, in `src/core/layout`) reads `useWindowDimensions()` and classifies `regular` when the width is ≥ 680pt, `compact` otherwise. Alternative dropped: exposing native `UITraitCollection.horizontalSizeClass` (truer to the HIG, but needs a new native module just for this). 680pt puts iPad mini in portrait (744pt) and any full-screen iPad as regular, iPhone (≤430pt) always compact, and narrow Split View (~1/3 to 1/2 of smaller screens) compact — revisiting the value is a constant tweak, not an architecture change.
- **Master-detail by composition, with the `Stack` always mounted.** `(main)/_layout.tsx` now always renders `<MasterDetailLayout sidebar={...}>{stack}</MasterDetailLayout>`, never the bare `Stack` as the root — `sidebar` is `null` in compact class (visually identical to today) and the session list in regular class. `MasterDetailLayout` (`src/ui`) always renders both slots (master possibly `null`, detail always present), so the `Stack` never changes parent when crossing the breakpoint — React never unmounts it, keeping the navigation stack (`session/[id]`, `terminal`, `agent/[agentId]`, `settings`) alive. Routes and `Stack.Screen`/`headerActions` stay exactly as they are today, with no screen needing a rewrite. Alternative dropped: Expo Router's `<Slot/>` in the detail pane — it would break every `<Stack.Screen options={headerActions(...)}/>` already used by the routes (title, action buttons), which only works with a real ancestor `Stack`. The `index` route (session list) now renders `SessionsScreen` itself only in compact class; in regular class it renders the detail pane's empty state, since the list is already visible in the master pane.
- **List selection comes from navigation state, not a second store.** The selected list item (`app-session-list` - "Selection in the master pane") is derived from the active child route (Expo Router's `usePathname()`), avoiding two sources of truth for "which session is open."
- **Orientation per idiom via `Info.plist`, not `expo-screen-orientation`.** Verified in `@expo/config-plugins`'s source (`ios/Orientation.ts`, `ios/DeviceFamily.ts`): Expo's `orientation` field only ever writes the unsuffixed `UISupportedInterfaceOrientations` key, never `UISupportedInterfaceOrientations~ipad`; `ios.supportsTablet` doesn't touch orientation at all (it only sets `TARGETED_DEVICE_FAMILY`). So the `orientation: 'portrait'` field stays in the config exactly as it is today (keeps iPhone locked to portrait through Expo's own native mechanism, with no risk of a plugin-ordering conflict), and a new config plugin (same pattern as `withSceneLifecycle`/`withFirebaseCocoaPods`) only *adds* the `UISupportedInterfaceOrientations~ipad` key (portrait + landscape) to `Info.plist` — a key Expo never writes, so there is no possible overwrite in any plugin execution order. Alternative dropped: `expo-screen-orientation` with a runtime lock conditional on `Platform.isPad` — works, but adds a runtime dependency and an extra effect for something that is purely declarative on iOS.
- **Pointer via `Pressable` (`onHoverIn`/`onHoverOut`), no new library.** React Native already exposes pointer events on `Pressable`; with no trackpad/mouse connected the callbacks simply never fire. Used on list items and shell buttons.
- **Hardware-keyboard shortcuts via `react-native-key-command`.** A library already used in production by RN apps to register `UIKeyCommand`s on iOS/iPadOS. Covers the shell shortcuts (Cmd+N, Cmd+,, Esc) and the Cmd+Enter in `app-conversation`'s prompt field. It needs a small, AppDelegate-level native hookup (see below) — confirmed working with a real build, not just assumed from the README. Alternative dropped: relying on `TextInput.onKeyPress`, which on iOS does not reliably expose modifier keys (Cmd) — it would catch a bare "Enter" but not distinguish Cmd+Enter from Enter.
- **The native hookup is config-plugin-driven, like the project's existing plugins.** `react-native-key-command` is a static pod (no `use_frameworks!` in this project's Podfile, confirmed by `grep`-ing the generated `Pods.xcodeproj` for `DEFINES_MODULE`), so its Objective-C `HardwareShortcuts` class is only visible to Swift through the project's bridging header, and `AppDelegate.swift` must implement `keyCommands`/`handleKeyCommand` (confirmed against the library's own native source, `HardwareShortcuts.m`/`KeyCommand.mm`, not just its README — UIKit asks the app delegate for `keyCommands` and dispatches by selector, and the library's singleton is not itself part of the responder chain). Two new config plugins add this: one appends the `#import` line to the generated bridging header (`withDangerousMod`, since `@expo/config-plugins` has no dedicated bridging-header mod), the other patches `AppDelegate.swift` (`withAppDelegate`, same string-replace pattern as the existing `withSceneLifecycle`). Verified with `expo prebuild --clean` plus a real `xcodebuild -sdk iphonesimulator build`, which reached `** BUILD SUCCEEDED **`.
- **Fixed, not proportional, reading width.** The conversation content's max width (`app-conversation` - "Reading width in wide panes") is a theme constant (`maxContentWidth`, a new token), not a percentage of the pane — this keeps diffs and code blocks from becoming absurdly wide on a 12.9" iPad without reintroducing a breakpoint calculation inside the screen itself.

## Risks / Trade-offs

- [`react-native-key-command` incompatible with the current Expo/RN version (57 / 0.86)] → resolved: a real `expo prebuild` + `xcodebuild` build succeeded with the library and its AppDelegate hookup in place.
- [680pt as a single breakpoint not fitting some real Split View size well] → isolated in a single function (`useWidthClass`), easy to adjust without touching the screens that consume it.
- [A future Expo upgrade starting to write `UISupportedInterfaceOrientations~ipad` on its own (today it does not, verified in source) and conflicting with the plugin] → covered by `npx expo export --platform ios` in CI (already used in the project) plus a manual check of the generated `Info.plist` as part of the tasks.
